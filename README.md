# Ticket Booking System

Ticket Booking System is a full-stack React and Express application for browsing movies and concerts, selecting seats from a venue layout, placing expiring holds, completing bookings, receiving QR tickets, and managing organiser and administrator workflows.

## Implemented capabilities

Customers can register, sign in, browse and filter events, optionally grant browser location permission to sort nearby events, inspect event details, select up to ten seats, hold seats for a configurable period, complete a booking, view QR tickets and booking history, cancel eligible bookings, join category-specific waitlists, and claim time-limited waitlist offers. Organisers can create and manage events, assign venues, and inspect event bookings and revenue. Administrators can manage users, venues, events, and platform bookings.

The seat map is stored per event in `ShowSeat` documents. Each seat has a label, row, column, category, server-calculated price, and one of `AVAILABLE`, `HELD`, or `BOOKED` states.

## Local setup

Install Node.js 18 or newer and MongoDB. A MongoDB replica set is required for the transactional hold, booking, acceptance, and cancellation workflows; a single-node replica set is sufficient for local development. Copy `.env.example` to `.env` and fill in at least `MONGODB_URI` and a long random `JWT_SECRET`.

```bash
npm install
npm run install:all
npm run dev
```

The client runs at `http://localhost:5173`, and the API runs at `http://localhost:5000`. The Vite development server proxies `/api` requests to the API. For separate processes, use `npm run dev:server` and `npm run dev:client`.

The development seed creates `admin@ticketbooking.com` with password `admin123` when no admin exists. Change or remove this account before production use.

Organisers can click **Use my location** on event creation or editing pages to request browser geolocation permission. Coordinate-enabled Indian venues are then returned in nearest-first order, with the distance shown in the venue selector. Organisers may deny permission and continue using the complete venue list. From **My Events**, organisers can delete events that have no confirmed bookings, or open **Edit or Reschedule Event** to update the event date and time. Rescheduling rejects past dates and invalid time ranges; deletion is rejected when confirmed bookings exist.

## Booking and concurrency design

A customer first requests an event’s seat labels. The server normalizes and validates labels, then uses a MongoDB transaction and conditional `updateMany` to change every requested seat to `HELD`. The conditional filter accepts only available seats, expired holds, or the same customer’s active hold. If every requested seat is not modified, the transaction aborts and the client receives HTTP 409; no partial multi-seat hold remains.

Booking confirmation runs in another transaction. It requires every requested seat to be held by the authenticated customer and to have a future expiry. The server calculates the total from persisted `ShowSeat.price`, creates the booking and QR payload, and atomically changes the seats to `BOOKED`. Cancellation uses a conditional confirmed-booking update and releases only seats belonging to that booking in the same transaction. These conditions prevent two concurrent customers from successfully claiming the same seat.

## Hold expiry and waitlists

Seat availability reads lazily release expired holds, and the cleanup loop repeats the same operation with an expiry predicate, making cleanup safe to retry. When a seat becomes available, the waitlist service selects the earliest `WAITING` entry for that event and category, atomically changes it to `OFFERED`, temporarily holds the seat for that customer, and stores only a SHA-256 hash of a random offer token. The email contains the raw token in a time-limited link. Acceptance requires the authenticated owner and valid token, renews the customer’s checkout hold, and changes the entry to `ACCEPTED` transactionally. Expired offers are marked `EXPIRED`, released, notified, and passed to the next queue entry.

The cleanup loop is intentionally database-backed and idempotent, but it runs inside the API process. For multiple production API instances, run cleanup as a single worker or scheduled job, or add a distributed lock around the cleanup entry point.

## API overview

| Method | Endpoint | Access | Purpose |
|---|---|---|---|
| `POST` | `/api/auth/register` | Public | Register a customer or organiser. |
| `POST` | `/api/auth/login` | Public | Return a JWT and user summary. |
| `GET` | `/api/events` | Public | Search, filter, and paginate events. |
| `GET` | `/api/events/:id` | Public | Read event and venue details. |
| `GET` | `/api/events?latitude=...&longitude=...` | Public | Return nearby events with distance in kilometres. |
| `GET` | `/api/venues?latitude=...&longitude=...` | Authenticated | Return nearby coordinate-enabled venues. |
| `POST` | `/api/seats/hold` | Customer | Atomically hold selected seats. |
| `GET` | `/api/seats/event/:eventId` | Authenticated | Read current seat states. |
| `POST` | `/api/seats/release` | Customer | Release the caller’s active holds. |
| `POST` | `/api/bookings` | Customer | Confirm held seats and generate a QR ticket. |
| `GET` | `/api/bookings` | Authenticated | Read the caller’s booking history. |
| `POST` | `/api/bookings/:id/cancel` | Customer | Cancel a confirmed booking. |
| `GET` | `/api/bookings/verify/:reference` | Public | Verify a booking reference and ticket status. |
| `POST` | `/api/waitlist` | Customer | Join an event/category queue. |
| `GET` | `/api/waitlist` | Authenticated | Read the caller’s waitlist entries. |
| `POST` | `/api/waitlist/:id/accept` | Customer | Accept a valid offer and receive a checkout hold. |
| `GET` | `/api/organiser/dashboard` | Organiser | Read organiser totals, revenue, and recent bookings. |
| `PATCH` | `/api/events/:id/reschedule` | Organiser/Admin | Reschedule an event to a future date and valid time range. |
| `DELETE` | `/api/events/:id` | Organiser/Admin | Delete an event when it has no confirmed bookings. |
| `GET` | `/api/admin/stats` | Admin | Read platform statistics. |

All protected endpoints expect `Authorization: Bearer <token>`. Validation failures use HTTP 400, authentication failures use 401, authorization failures use 403, missing records use 404, and concurrency conflicts use 409.

## Testing

Run deterministic unit tests with:

```bash
npm test --prefix server
```

The suite covers seat-label normalization, the seat-count limit, and one-way waitlist token hashing. Integration tests for concurrent holds, booking confirmation, cancellation, and expiry cleanup run when `MONGODB_TEST_URI` points to an isolated MongoDB replica set. They intentionally remain skipped when no test database is configured.

The client production build is verified with:

```bash
npm run build --prefix client
```

## Deployment checklist

Build the client with `npm run build --prefix client` and deploy `client/dist` to a static host such as Vercel; browser location access should be tested on `localhost` or an HTTPS deployment. The location feature is optional and manual event browsing remains available when permission is denied.  `client/vercel.json` preserves client-side routes on refresh. Deploy the `server` directory as a Node service on a host such as Render or Railway. The optional `render.yaml` describes the API service and its health check. Set the environment variables in the hosting provider, and point `MONGODB_URI` to a managed MongoDB replica set. Set `CLIENT_URL` to the deployed client origin and configure the client’s production API proxy or same-origin reverse proxy for `/api`.

For a horizontally scaled API, run expiry cleanup in one worker rather than every instance, use a shared MongoDB deployment, configure a stable HTTPS origin, and set restrictive CORS and secrets. Email delivery failures are logged after successful booking persistence so a temporary SMTP problem does not roll back a confirmed booking.
